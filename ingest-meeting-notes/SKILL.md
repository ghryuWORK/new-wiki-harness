# Ingest Meeting Notes (회의록 Wiki 자동화)

Raw 회의록을 읽고 **규칙 기반**으로 Wiki 항목을 자동 생성/업데이트하는 스킬입니다.

## 목적

회의가 끝나면 Raw 회의록이 `raw/` 폴더에 저장됩니다. 이 스킬은:

1. **회의록 분석** → 결정/액션/보류 항목 추출
2. **규칙 적용** → CLAUDE.md의 DO/DON'T 규칙 + wiki/스키마.md v1.1 따르기
3. **Wiki 생성** → wiki/ 폴더에 D-xxx, A-xxx, P-xxx 파일 자동 생성
4. **상태 추적** → 다중 회의 항목의 상태 변화 기록
5. **문제 감지** → 미추적, 블로킹, 리소스 충돌 자동 발견

**핵심 원칙**: Raw는 불변의 원본. Wiki는 파생 계층. 문제점을 명시하는 것이 개선입니다.

---

## 사용 방법

### 새 회의록 ingest
```
새로운 회의록이 raw/ 폴더에 저장되면:
/ingest raw/2026-05-14-제품주간회의.md
```

### 전체 폴더 처리
```
/ingest raw/
```

---

## 상세 작동 방식

### 단계 1: 회의록 분석

Raw 회의록(YAML 메타데이터 + 마크다운)을 읽고:

- **메타데이터 추출**
  ```yaml
  출처: Notion | 직접기록
  회의일: 2026-05-14
  가져온시점: 2026-05-14
  참석: 이지혜(PM), 박준서(개발), ...
  ```

- **섹션 파싱**
  - `## 안건`: 논의할 주제들
  - `## 결정`: "~하자", "~로 결정했다" 패턴 찾기
  - `## 액션 아이템`: `- [ ] 이름 — 할일 (~기한)` 형식
  - `## 기타`: 담당자/기한 없는 미해결 사항

### 단계 2: 항목 분류

각 항목을 D(결정) / A(액션) / P(보류) 중 하나로 분류:

| 분류 | 조건 | 예시 |
|------|------|------|
| **D-xxx** | 명시적 결정, 의사결정자 명확 | "PG사를 A사로 선정했다" |
| **A-xxx** | 명확한 담당자 + (대부분) 기한 | "박준서 - 스펙 문서 확보 (~5/21)" |
| **P-xxx** | 담당자 미정 OR 기한 불명확 | "재무팀과 정산 프로세스 확인" (담당자 미정) |

### 단계 3: ID 할당

기존 wiki 파일을 확인해서 다음 번호 자동 결정:
- 마지막 D 파일이 D-004면 → 새 항목은 D-005
- 마지막 A 파일이 A-005면 → 새 항목은 A-006
- 마지막 P 파일이 P-001면 → 새 항목은 P-002

**규칙**: 같은 타입 내에서 순증가. 번호는 재사용하지 않음.

### 단계 4: Status 결정 (규칙 기반)

wiki/스키마.md v1.1의 Status 값을 따름:

**Decision Status**:
- `open`: 결정됐으나 진행 중
- `closed`: 완료됨
- `pending`: 선행 조건 대기
- `pending_implementation`: 의사결정은 됐으나 미시작
- `in_progress`: 분석/논의 진행 중
- `unclear`: 상황 불명
- `at_risk`: 기한/조건 위험

**Action Status**:
- `open`: 할당됐으나 미시작
- `in_progress`: 진행 중
- `completed`: 완료됨
- `blocked`: 다른 작업에 의해 진행 불가
- `on_hold`: 의도적 일시 중단
- `at_risk`: 기한 임박/완료 불확실
- `untracked`: 진행 상황 미보고

**Pending Status**:
- `pending`: 진행 대기
- `stalled`: 진행 안 됨
- `escalated`: 상위 보고

**규칙 적용**:
- 회의록에 명시된 상태 있으면? → 그 상태 사용
- 없으면? → 스킬이 맥락에서 추론
  - 예: "스펙을 받아야 착수 가능" → pending (A-003)
  - 예: "기한이 지났으나 미보고" → untracked (A-002)

### 단계 5: Wiki 파일 생성

**Decision (D-xxx.md)**:
```yaml
---
id: D-001
source: raw/2026-05-14-제품주간회의.md
title: "의사결정 제목"
owner: 담당자 또는 의사결정자
status: open|closed|pending|...
created_date: 2026-05-14
last_modified: (수정되지 않았으면 생략)
---

## 내용
의사결정의 핵심 1-2문장.

## 배경
왜 이 결정이 필요했는가?

## 의사결정 세부사항
- 의사결정자: 이지혜
- 근거: ...
- 날짜: 2026-05-14

## 현재 상태
- 구현 여부: ...
- 마지막 업데이트: ...

## 연관 항목
- [[A-003]]: ...
- [[D-002]]: ...
```

**Action (A-xxx.md)**:
```yaml
---
id: A-001
source: raw/2026-05-14-제품주간회의.md
title: "액션 제목"
owner: 담당자
status: open|in_progress|...
created_date: 2026-05-14
due_date: 2026-05-21
---

## 액션 내용
구체적으로 무엇을 해야 하는가?

## 기한
- 할당일: 2026-05-14
- 기한: 2026-05-21

## 진행 상황
- 현재: 미시작 / 진행 중 / 완료
- 마지막 업데이트: ...

## 영향도
이 액션이 영향을 미치는 것들 (예: D-003)

## 연관 항목
- [[D-003]]: ...
```

**Pending (P-xxx.md)**:
```yaml
---
id: P-001
source: raw/2026-05-14-제품주간회의.md
title: "보류 사항"
owner: unassigned (또는 이름)
status: pending|stalled|escalated
created_date: 2026-05-14
---

## 문제 설명
무엇이 미해결되었는가?

## 배경
왜 보류되었는가?

## 현재 상태
- 담당자: 미정
- 기한: 미정

## 영향도
이것이 해결되지 않을 경우의 영향.
```

### 단계 6: 다중 회의 항목 처리

같은 항목이 여러 회의에 등장하면 → **상태 변화 섹션 추가**:

```markdown
## 상태 변화
- 2026-04-16: 원래 상태/할당됨
- 2026-05-14: 상태 변경 (사유: ...)
- ...
```

예시:
- A-002가 2026-04-16에 할당되었으나 2026-05-14 회의에서 미보고 → status: untracked + 상태 변화 섹션
- D-003이 2026-04-16에 "5월 말"로 설정되었으나 2026-05-14에 "6월 중순"으로 연기 → status: at_risk + 상태 변화 섹션

### 단계 7: 문제 자동 감지 (CLAUDE.md 기반)

스킬이 다음을 감지하고 경고:

| 문제 | CLAUDE.md 규칙 | 대응 |
|------|----------------|------|
| 액션인데 Owner 없음 | W-DO-4 | P-xxx로 전환 제안 |
| 액션인데 기한 없음 | W-DO-5 | P-xxx로 전환 제안 |
| 여러 회의에 나왔으나 미추적 | F-DO-1 | "상태 변화 섹션 추가" 권장 |
| 블로킹 관계 있음 | RS-DO-1 | "리소스/의존성 섹션 필수" 표시 |
| 선행 조건 미확인 상태로 결정 | D-1 | "선행 조건 확인 필수" 경고 |

## 출력 형식

### 성공 케이스
```
✅ ingest 완료: raw/2026-05-14-제품주간회의.md

📊 생성된 항목 (4개):
  ✓ D-002 정산 주기 (owner: 강태우)
  ✓ A-001 PG사 비교표 (owner: 박준서)
  ✓ A-002 계약 조건 (owner: 강태우)
  ✓ P-001 정산 프로세스 (owner: unassigned)

⚠️ 경고 & 권장사항 (2개):
  ⚠️ A-002: 담당자는 있으나 기한 없음 (W-DO-5)
     → P-xxx로 전환할지, 아니면 기한 추가할지 검토 필요

  ⚠️ A-004: 2026-04-16부터 있었으나 2026-05-14 회의에서 상태 변화 무시됨
     → status: untracked 제안 + "상태 변화 섹션" 추가 권장

🔗 감지된 연관 관계:
  D-003 (결제 연동 연기) ← A-003 필수 (스펙 문서)
  A-004 (대시보드) ← A-005 리소스 충돌 (최민아 동시 불가)
  D-002 (PG사 선정) ← A-002 미충족 전제조건 (계약 조건 미검토)
```

### 문제가 있는 경우
```
⚠️ ingest 불완전: raw/2026-05-14-제품주간회의.md

❌ 심각한 문제 (진행 불가):
  - 메타데이터 누락: 참석자 정보 없음
  - ## 안건 섹션 없음

✅ 부분적으로 생성된 항목:
  (문제 있는 항목들)

💡 다음 단계:
  1. Raw 회의록 보완
  2. 다시 ingest 실행
```

## 제약사항 및 주의사항

### 읽을 파일
- ✅ `CLAUDE.md` (운영 규칙)
- ✅ `wiki/스키마.md` (Wiki 스키마 v1.1)
- ✅ `raw/YYYY-MM-DD-회의명.md` (대상 회의록)
- ✅ 기존 `wiki/` 폴더 (ID 번호 결정용)

### 읽지 않을 파일
- ❌ `hands_over/` (설계 과정 문서, 핸즈오버용)
- ❌ Git history (버전 관리)
- ❌ `.git/` 폴더

### 중요 규칙
1. **Raw는 절대 수정하지 말 것** (SSOT 원칙)
2. **ID 번호는 순증가만 가능** (재사용 금지)
3. **Status는 스키마 v1.1의 7개 값만 사용**
4. **문제점은 명시하기** (숨기지 않기)
5. **연관 항목은 반드시 링크** (의존도 명확화)

## 예상 사용 시나리오

### 시나리오 1: 새 회의 후
```
회의 끝남 → raw/2026-05-14-제품주간회의.md 저장
        → /ingest raw/2026-05-14-제품주간회의.md
        → Wiki 항목 자동 생성 + 보고서 제시
        → 팀원들이 Wiki를 통해 상황 파악
```

### 시나리오 2: 재 ingest (상태 추적)
```
같은 회의록을 다시 ingest → 기존 항목은 status 업데이트
                      → "상태 변화" 섹션 자동 추가
                      → 새로운 문제점 감지
```

### 시나리오 3: 전체 폴더
```
/ingest raw/ → 모든 회의록을 한 번에 처리
           → 전체 시스템 상태 파악 가능
```
