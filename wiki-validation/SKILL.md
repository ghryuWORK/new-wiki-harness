# Wiki 컨텐츠 검증 (LLM Review)

Wiki 항목(D/A/P)과 원본 회의록을 비교하여 **일치성, 누락, 추적 상태**를 검증하는 스킬입니다.

## 목적

기계 검증(스크립트)이 형식을 확인했다면, 이 스킬은 **의미 수준**에서 검증합니다:

1. **회의록과의 일치성**: Wiki가 원본 회의록을 정확히 반영했는가?
2. **생성 오류 감지**: 회의록에 없는 내용을 Wiki에 만들지 않았는가?
3. **중요 내용 누락**: 결정/액션/보류의 핵심이 빠지지 않았는가?
4. **상태 추적 정확성**: 다중 회의 항목의 상태 변화가 올바른가?
5. **액션 추적**: 열림/홀드/사라짐 등의 상태가 명확하게 추적되었는가?

---

## 사용 방법

### 단일 Wiki 항목 검증
```bash
/wiki-content-review wiki/결정/D-001.md
```

### 특정 유형 전체 검증
```bash
/wiki-content-review wiki/액션아이템/
/wiki-content-review wiki/보류/
```

### 전체 Wiki 검증
```bash
/wiki-content-review wiki/
```

## 실행 절차 (Agent가 따를 단계)

사용자가 `/wiki-content-review <path>` 명령을 실행하면 Agent는 아래 단계를 순서대로 따릅니다.

### 📋 입력 단계

**사용자 입력 해석**:
- `wiki/액션아이템/A-001.md` → 단일 파일 검증
- `wiki/결정/` → 해당 폴더의 모든 .md 파일
- `wiki/` → 모든 D/A/P 파일 (재귀적)

**파일 목록 생성**:
- Glob으로 모든 대상 파일 수집
  - `wiki/결정/D-*.md`
  - `wiki/액션아이템/A-*.md`
  - `wiki/보류/P-*.md`

---

### 🔍 각 Wiki 파일 검증 (반복)

**Step 1: Wiki 파일 읽기 및 메타데이터 추출**

Read 도구로 Wiki 파일 전체 읽기:
```yaml
---
id: A-001
source: raw/2026-04-16-제품주간회의.md
title: "제목"
owner: 담당자명
status: open
created_date: 2026-04-16
due_date: 2026-04-21
---

## 본문 섹션들...
```

**추출할 정보**:
- `id`: 항목 ID
- `source`: 원본 회의록 (단일 또는 다중: `file1.md → file2.md`)
- `title`, `owner`, `status`, `created_date` 등
- 본문의 주요 섹션 확인

---

**Step 2: 원본 회의록 읽기**

source 필드에서 회의록 파일 추출:
- 단일: `raw/2026-04-16-제품주간회의.md` → 1개 파일 읽기
- 다중: `raw/2026-04-16-제품주간회의.md → raw/2026-05-14-제품주간회의.md` → 2개 파일 읽기

**각 회의록에서 찾을 것**:
- 메타데이터 (회의일, 참석자)
- 이 Wiki 항목과 대응되는 부분 (발언, 결정, 액션, 기타)

**없으면**:
- ❌ "source 파일 없음" 경고 기록

---

**Step 3: 검증 수행 (A-E 항목 확인)**

아래의 검증 항목(A~E)에 따라 회의록과 Wiki를 비교:

#### **A. 일치성 검증**
- ✅ 회의록의 해당 부분이 Wiki와 정확히 일치하는가?
- ✅ source 파일이 실제로 존재하는가?
- ✅ owner, created_date가 회의록과 맞는가?
- 점수: 완전 일치(✅) / 부분 일치(⚠️) / 불일치(❌)

#### **B. 생성 오류 감지**
- ❌ Wiki에는 있지만 회의록에는 없는 내용?
- ❌ "아마도", "생각해볼 수 있음" 같은 추정 표현?
- ❌ 회의에서 나오지 않은 외부 정보 삽입?
- 점수: 없음(✅) / 미미(⚠️) / 심각(❌)

#### **C. 누락 감지**
- ❌ 핵심 내용이 빠졌는가?
  - 결정: 근거(왜?)가 명확한가?
  - 액션: 담당자, 기한, 구체적 내용이 있는가?
  - 보류: 원인이 설명되어 있는가?
- ❌ 선행 조건/리소스 충돌이 표시되어 있는가?
- 점수: 없음(✅) / 경미(⚠️) / 중요(❌)

#### **D. 상태 추적 정확성 (다중 회의 항목인 경우)**
- 다중 회의: source에 여러 파일이 있는가? (`→` 포함)
  - Yes → "상태 변화" 섹션이 있는가?
  - 섹션의 날짜, 사유, 타임라인이 정확한가?
- 점수: 완벽 추적(✅) / 부분 추적(⚠️) / 미추적(❌)

#### **E. 액션만: 상태 추적**
- `open`: 수개월 경과해도 open? (at_risk 표시 필요)
- `in_progress`: 마지막 업데이트가 2주 이상 전?
- `blocked`: 블로킹 사유가 명시되어 있는가?
- `on_hold`: 홀드 복귀 예정일이 명확한가?
- `untracked`: 얼마나 오래 미보고인가?
- 점수: 명확(✅) / 부분 명확(⚠️) / 불명확(❌)

---

**Step 4: 개별 리포트 생성**

각 파일마다 결과를 정리:
```
📄 wiki/액션아이템/A-001.md

✅ 일치성: 완벽 (회의록과 정확히 일치)
✅ 생성 오류: 없음
✅ 누락: 없음
✅ 상태 추적: 완벽
✅ 액션 추적: 명확

점수: 5/5 ⭐⭐⭐⭐⭐
```

또는 문제가 있으면:
```
⚠️ wiki/액션아이템/A-002.md

⚠️ 일치성: 부분 일치
❌ 생성 오류: 1개 (미미)
❌ 누락: 2개 (중요)
⚠️ 상태 추적: 부분 추적

점수: 2/5 ⭐⭐

발견사항:
  ❌ 기한 경과: 104일 (기한 2026-04-30 → 현재 2026-08-10)
  ⚠️ 상태 변화 섹션 불완전
  ...
```

### 📊 종합 리포트 생성

모든 파일 검증 완료 후:

1. **파일별 결과를 우선순위 순으로 정렬**:
   ```
   ❌ 심각 (0-1점)
   ⚠️ 경고 (2-4점)
   ✅ 완벽 (5점)
   ```

2. **통계**:
   ```
   총 N개 파일 검증
   - ✅ 완벽: M개
   - ⚠️ 경고: K개
   - ❌ 심각: L개
   평균 점수: X.X/5 ⭐⭐⭐
   ```

3. **주요 개선점 (패턴 찾기)**:
   ```
   가장 많은 문제 유형:
   1. 상태 변화 타임라인 불완전 (N개 파일)
   2. 기한 경과 미표시 (K개 파일)
   3. 리소스 충돌 명시 부족 (L개 파일)
   ```

4. **최종 권장사항**:
   ```
   다음 우선순위 개선:
   - [ ] A-002: 기한 경과 상태 업데이트
   - [ ] D-003: 선행 조건 명시
   - [ ] P-001: 담당자/기한 할당
   ```

## 도구 사용 가이드

Agent가 이 스킬을 실행할 때 사용할 도구:

| 단계 | 도구 | 사용 목적 |
|------|------|---------|

| 검색 (필요시) | Grep | 특정 내용 확인 (예: 액션 상태) |

**하지 말 것**:
- ❌ Wiki/Raw 파일 수정 (검증만 수행)
- ❌ 새 파일 생성
- ❌ 추정이나 추론으로 내용 보충

## 출력 형식

### 검증 완료 (문제 없음)
```
✅ wiki/결정/D-001.md 검증 완료

📋 검증 결과:
  ✅ 일치성: 완벽 (회의록과 정확히 일치)
  ✅ 생성 오류: 없음
  ✅ 누락: 없음
  ✅ 상태 추적: 완벽
  ✅ 액션 추적: 명확 (at_risk 표시 적절)

점수: 5/5 ⭐⭐⭐⭐⭐
```

### 문제 발견 (경고)
```
⚠️ wiki/액션아이템/A-002.md 검증 완료

📋 검증 결과:
  ✅ 일치성: 부분 일치
  ⚠️ 생성 오류: 미미 (1개)
  ❌ 누락: 중요 (2개)
  ⚠️ 상태 추적: 부분 추적
  ⚠️ 액션 추적: 불명확

점수: 2/5 ⭐⭐

🔍 상세 발견사항:

❌ 누락 - 선행 조건:
  • Wiki에는 "진행하려면 D-003 필요"라는 내용이 있지만, 
    실제 회의록(2026-05-14)에서는 이 관계가 명시되지 않았음
  • 권장: 회의록을 다시 확인하고, 관계가 없다면 Wiki에서 제거

⚠️ 생성 오류 - 추론 과다:
  • Wiki의 "의사결정 세부사항" 섹션에서:
    "수수료가 2.2%로 가장 저렴"이라고 기록했으나,
    원본 회의록(2026-04-16)에서는 "수수료 비교는 아직"이라고 함
  • 권장: 실제 수수료 비교 회의(예: 2026-05-14)에서 확인되었다면 
    그 출처를 source 필드에 추가하기

❌ 누락 - 기한 경과 추적:
  • 할당: 2026-04-16, 기한: 2026-04-30
  • 현재: 2026-08-10 (3개월 이상 경과)
  • Wiki의 "진행 상황" 섹션에 "기한 경과: 105일" 같은 표시 없음
  • 권장: status: untracked + 상태 변화 섹션에 기한 경과 기록

⚠️ 상태 추적 - 불완전한 타임라인:
  • 상태 변화 섹션에:
    - 2026-04-16: 할당됨
    - 2026-05-14: 미보고
    (중간의 2026-04-20, 2026-05-07 같은 중간 보고 없음)
  • 권장: 회의록에 중간 언급이 있는지 확인하고 추가
```

### 다중 파일 검증
```
📊 Wiki 컨텐츠 검증 리포트
검증 대상: wiki/액션아이템/ (7개 파일)

✅ 완벽 (5-5점): 3개
  • A-001: PG사 비교표
  • A-006: Q3 대시보드 스펙
  • A-007: 온보딩 분석

⚠️ 경고 (2-4점): 3개
  • A-002: 계약 조건 (누락: 선행 조건, 기한 경과 미표시)
  • A-003: 리소스 충돌 표시 미흡
  • A-005: 상태 변화 타임라인 불완전

❌ 심각 (0-1점): 1개
  • A-004: on_hold 복귀 시점 명확하지 않음 (2개월 경과)

💡 종합 피드백:
  • 전체 평균: 3.9/5 ⭐⭐⭐⭐
  • 주요 개선점:
    1. 액션의 상태 변화 섹션을 더 상세히 (특히 미보고 항목)
    2. 기한 경과 항목에 "지연 기간" 필드 추가
    3. 리소스 충돌/블로킹 관계를 명시적으로 표시
```

## 검증 체크리스트

### Decision (D-xxx) 검증
- [ ] 회의록의 해당 부분을 찾을 수 있는가?
- [ ] 의사결정자가 명확한가?
- [ ] "왜 이 결정을 했는가"(근거)가 설명되어 있는가?
- [ ] 현재 상태(구현됨/진행 중/미실행)가 명확한가?
- [ ] 선행 조건이 있다면 명시되어 있는가?
- [ ] 다중 회의 항목이면 "상태 변화" 섹션이 있는가?
- [ ] 연관 항목(다른 D/A/P)이 링크되어 있는가?

### Action (A-xxx) 검증
- [ ] 회의록의 해당 부분을 찾을 수 있는가?
- [ ] 담당자가 명확한가?
- [ ] 기한이 명확한가?
- [ ] "구체적으로 무엇을"(내용)이 명확한가?
- [ ] 현재 상태(open/in_progress/completed/...)가 정확한가?
- [ ] 상태가 "blocked"라면 블로킹 사유가 명시되어 있는가?
- [ ] 상태가 "on_hold"라면 복귀 예정일이 명시되어 있는가?
- [ ] 상태가 "untracked"라면 얼마나 오래 미보고인지 기록되어 있는가?
- [ ] 다중 회의 항목이면 "상태 변화" 섹션이 있는가?
- [ ] 리소스 충돌이 있다면 "리소스/의존성" 섹션이 있는가?
- [ ] 영향도(이 액션의 결과가 뭔가)가 기록되어 있는가?

### Pending (P-xxx) 검증
- [ ] 회의록의 해당 부분을 찾을 수 있는가?
- [ ] 미해결 사항이 명확한가?
- [ ] "왜" 보류되었는가(원인)이 설명되어 있는가?
- [ ] 담당자가 명시되어 있는가? (unassigned 표시)
- [ ] 해결되지 않을 경우의 영향이 설명되어 있는가?

## 주의사항

### 읽을 파일
- ✅ `raw/YYYY-MM-DD-*.md` (Wiki의 source에 명시된 모든 회의록)
- ✅ `wiki/결정/D-xxx.md` (검증 대상)
- ✅ `wiki/액션아이템/A-xxx.md` (검증 대상)
- ✅ `wiki/보류/P-xxx.md` (검증 대상)

### 하지 않을 것
- ❌ Wiki 파일을 수정하지 말 것 (리뷰만 수행)
- ❌ Raw 회의록을 수정하지 말 것 (원본 유지)
- ❌ 개별 회의록의 구성을 판단하지 말 것 (회의록은 있는 그대로 수용)

## 예상 사용 시나리오

### 시나리오 1: 새 Wiki 항목 생성 후
```
회의록 ingest 완료 → /wiki-content-review wiki/
                 → 각 D/A/P의 일치성/누락/상태 검증
                 → 리포트 제시
```

### 시나리오 2: 상태 업데이트 후
```
A-002 상태를 "untracked"로 변경 → /wiki-content-review wiki/액션아이템/A-002.md
                           → 상태 변화 타임라인 검증
                           → 기한 경과 기록 확인
```

### 시나리오 3: 다중 회의 항목 점검
```
같은 항목이 3개 회의(04-16, 05-14, 06-11)에 걸쳐 존재
→ /wiki-content-review wiki/결정/D-003.md
→ 3개 회의의 내용이 모두 반영되었는지 검증
→ 상태 변화가 정확한지 확인
```
